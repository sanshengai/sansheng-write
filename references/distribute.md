# 一稿多投 · 分发层

公众号定稿之后的**第二段链路**：同一篇文章派生到小红书、微博、播客。

引擎 `scripts/distribute.py`，渠道配置在 profile 的 `brand.yaml` → `distribute:`。

## 定位与边界

```
release-runtime  定稿 → 排版 → 视觉 → 微信草稿箱 → finalize（永久链接 + 归档 + 官网）
                                                        │
distribute                                              └─→ 小红书 / 微博 / 播客
```

- **上游只有一个**：`定稿.md`。各渠道从它派生，不允许"为某个平台单独写一版"——那样迟早出现同一篇文章在三个平台说法不一致。
- **起点是 finalize 之后**：分发文案要带公众号永久链接。没跑 finalize 也能 plan，但链接会留空，`status` 会提示。
- **不接管人工判断**：正式发布仍由作者完成；能自动的只有微博。

## 🔴 核心认知：这不是"把文章搬过去"

多渠道分发最容易犯、也最贵的错，是把长文原样切块投出去。

- **小红书对搬运感极其敏感**。按段落切成 9 张图 = 图文质量分被压，推荐量直接腰斩。正确做法是**重新讲一遍**：换叙事节奏、换情绪曲线，只保留内核。这套提炼方法在 [xhs-storyboard.md](xhs-storyboard.md)，别绕过它自己切。
- **微博不是短版公众号**。140 字之内要能独立成立，读者划到就懂，不靠点进原文补全。
- **播客不是文章朗读**。文字是"看的逻辑"，音频是"听的逻辑"——听众没法回看上一句，所以需要重复、口语过渡和更慢的信息密度。这件事交给 NotebookLM 的双主持形式解决，但**主持风格提示词决定成败**（见下）。

一句话：**一鱼多吃吃的是内核，不是同一块肉切三刀。**

## 三段式工作流

脚本做闸门，agent 做内容——与本 skill 其余部分同一套分工。

```bash
python "$SKILL/scripts/distribute.py" status            # 各渠道状态
python "$SKILL/scripts/distribute.py" plan              # 产约束 + 待填槽
#   ↓ agent 按下面的口径表填 dist/<渠道>/文案.txt
python "$SKILL/scripts/distribute.py" verify <渠道>      # 硬门，不过 exit 2
python "$SKILL/scripts/distribute.py" dispatch <渠道>    # 默认 dry-run，真发要 --confirm
```

产物目录（统一收在 `dist/` 下，与文章其余产物分开）：

```
{文章目录}/dist/
  ├── _distribute-plan.json     # 计划：各渠道约束 + 上游 digest
  ├── _distribute-state.json    # 状态机：pending→planned→drafted→verified→dispatched
  ├── xhs/     文案.txt  images/  xhs-outline.md  _receipt.json
  ├── weibo/   文案.txt  _receipt.json
  └── podcast/ audio.mp3  shownotes.md  _receipt.json
```

**文案文件格式**（纯文本，故意不用 YAML——它的最终用途就是被整段选中贴进平台输入框，多一层语法就多一次贴错的机会）：

```
第一段是标题（微博无标题则此段即正文首段）

正文……

#标签 #标签
```

## 渠道口径表（🔴 三个平台的差异，填文案前必读）

| | 小红书 | 微博 | 播客 |
|---|---|---|---|
| 标题 | ≤20 字，**是搜索入口**，要带关键词 | 无独立标题 | 单集标题 ≤60 字 |
| 正文 | ≤1000 字，参与搜索排名，**不是可选项** | **≤140 字**，超了折叠成「展开全文」 | shownotes ≤800 字 |
| 标签 | `#标签`（无尾井号），≥4 个 | `#话题#`（**前后都要**），≥2 个 | 无 |
| 图片 | 6-16 张轮播，主战场 | ≤4 张（自动九宫格） | 单张封面 |
| 链接 | 正文不能放外链（会被限流），引导「主页」 | 可放，自动转 t.cn 短链**占约 25 字** | shownotes 可放 |
| 发布 | **只能人工**（无开放接口） | 可自动（Chrome CDP） | 自建 RSS，平台侧抓取 |

**易错点**：

- 🔴 标签格式两边**反着**：小红书 `#读书`，微博 `#读书#`。写反了 verify 会拦，但别指望它——两套文案分开写，不要复制粘贴改一改。
- 🔴 微博的 140 字算的是**全文**，标签和短链都计入。留出余量。
- 🔴 小红书正文放外链会限流。原文入口靠「主页简介」或评论区，不写进正文。

## 各渠道执行要点

### 小红书

1. 先按 [xhs-storyboard.md](xhs-storyboard.md) 产 `dist/xhs/xhs-outline.md`（金句锁定 → 情绪曲线 → 分镜编排）。
2. 交 `baoyu-xhs-images` 生图，输出到 `dist/xhs/images/`，分辨率 1K（1242×1660）。
3. 正文文案**不是图片的说明文字**，是独立的一段——首句要能单独抓住划到的人。
4. `dispatch` 只产手动发布包并打印路径；作者发完后 `--confirm` 登记凭证。

### 微博

1. 图直接复用小红书那套的前 4 张（封面 + 3 张信息量最大的），不另生成。
2. 正文写法：**一个完整的判断 + 一个具体数字或细节**。不写"点击阅读全文了解更多"这种话。
3. `dispatch --confirm` 走 `baoyu-post-to-weibo`（Chrome CDP）。
   > 🔴 别因为"微博 API 要 OAuth、token 5-7 天就过期"而退回半自动——那个结论只对
   > 官方 API 成立。CDP 路径走真实浏览器会话，没有 token 过期问题。

### 播客

1. **喂裸定稿 markdown 给 NotebookLM，不做二次提炼**——晨报链路验证过，提炼一遍反而丢细节。
2. 🔴 **主持风格提示词必须新写**，profile 的 `podcast.focus_prompt` 指向它。晨报那份是"双主持播报 10 条要闻"的节奏，文章是"两个人聊透一个话题"，照搬会得到一个结构很怪的节目。
3. 生成 → 转码 mp3 → 落 `episodes_dir` → 重建 `feed.xml` → 平台侧 1-12 小时自动抓取。
4. 🔴 **必须与晨报节目用独立的 feed、独立的目录、独立的锁文件**。共用锁会让两条链路互相踩。

## 渠道适配器接线状态

骨架阶段 `dispatch --confirm` 对 `auto` / `rss` 渠道**明确报未接线并 exit 3**，不写假装成功的桩——状态机记下一次没发生过的发布，比不发布更糟。

| 渠道 | 状态 | 接线要做的事 |
|---|---|---|
| 小红书 | ✅ 可用 | 手动发布包已完整，无需接线 |
| 微博 | ⬜ 未接线 | 在 `cmd_dispatch` 调 `baoyu-post-to-weibo` 的 `weibo-post.ts`，传文案与图片路径，成功后写 receipt |
| 播客 | ⬜ 未接线 | 需先定节目名、建第二个 feed、写 `focus_prompt`；再把 NotebookLM 调用与 feed 重建接进来 |

## 铁律

1. **上游漂移即失效**：`定稿.md` 一变，所有已生成的分发文案标记过期，`verify` 与 `dispatch` 双双阻断。改了文章就得重做文案，没有例外。
2. **没有 receipt 就不算发过**：状态机只认凭证文件，不认口头登记。
3. **`dispatch` 默认 dry-run**：对外发布不可撤回，真发必须显式 `--confirm`。
4. **私有值只进 profile**：账号名、feed 主机、节目 ID 属于「私有但非密」，与品牌 token 同层；密钥仍然只走 `.env`。公开仓的 `profile.example` 只留占位。
5. **不为「能自动」牺牲账号安全**：小红书没有开放接口就是没有，不去驱动 UI 自动化冒充自动发布。
