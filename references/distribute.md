# 一稿多投 · 分发层

公众号定稿之后的**第二段链路**：同一篇文章派生到小红书、微博、播客。

引擎 `scripts/distribute.py`，渠道配置在 profile 的 `brand.yaml` → `distribute:`。

## 定位与边界

```
release-runtime  定稿 → 排版 → 视觉 → 微信草稿箱 → finalize（永久链接 + 归档 + 官网）
                                                        │
distribute                                              └─→ 小红书 / 微博 / 播客
```

- **上游只有一个**：`定稿.md`。各渠道从它派生，不允许"为某个平台单独写一版"——那样迟早出现同一篇文章在三个平台说法不一致。
- **起点是 finalize 之后**：分发文案要带公众号永久链接。没跑 finalize 也能 plan，但链接会留空，`status` 会提示。
- **最后一下永远是人点的**：脚本把内容填进发布框就停手，正式发布由作者确认。填错了还能改，发出去收不回来。

## 🔴 核心认知：这不是"把文章搬过去"

多渠道分发最容易犯、也最贵的错，是把长文原样切块投出去。

- **小红书对搬运感极其敏感**。按段落切成 9 张图 = 图文质量分被压，推荐量直接腰斩。正确做法是**重新讲一遍**：换叙事节奏、换情绪曲线，只保留内核。提炼方法在 [xhs-storyboard.md](xhs-storyboard.md)，别绕过它自己切。
- **微博不是短版公众号**。140 字之内要能独立成立，读者划到就懂，不靠点进原文补全。
- **播客不是文章朗读**。文字是"看的逻辑"，音频是"听的逻辑"——听众没法回看上一句，所以需要重复、口语过渡和更慢的信息密度。

一句话：**一鱼多吃吃的是内核，不是同一块肉切三刀。**

## 三段式工作流

脚本做闸门，agent 做内容——与本 skill 其余部分同一套分工。

```bash
python "$SKILL/scripts/distribute.py" status            # 各渠道状态
python "$SKILL/scripts/distribute.py" plan              # 产约束 + 待填槽
#   ↓ agent 按下面的口径表填 dist/社媒文案.txt
python "$SKILL/scripts/distribute.py" verify <渠道>      # 硬门，不过 exit 2
python "$SKILL/scripts/distribute.py" dispatch <渠道>    # 默认 dry-run，真跑要 --confirm
```

产物目录：

```
{文章目录}/dist/
  ├── 社媒文案.txt              # 小红书 + 微博两段（格式见下）
  ├── _distribute-plan.json     # 计划：各渠道约束 + 上游 digest
  ├── _distribute-state.json    # 状态机：pending→planned→drafted→verified→dispatched
  ├── xhs/     images/  xhs-outline.md  _receipt.json
  ├── weibo/   _receipt.json
  └── podcast/ audio.mp3  shownotes.md  _receipt.json
```

### 文案文件格式

**与晨报的 `社媒文案.txt` 逐字一致**——同一套分隔符、同一套小节名。这不是巧合：
两边共用同一批发布脚本，格式一致才能复用，作者的肌肉记忆也一致。

```
════════════ 小红书 ════════════

# 标题

<≤20 字，按小红书算法计数>

# 正文

<正文，含 #标签>


════════════ 微博 ════════════

# 正文

<≤140 字，含 #话题#>
```

纯文本而非 YAML 是有意的：这些内容的最终用途就是被整段贴进平台输入框，多一层语法就多一次贴错的机会。

## 渠道口径表（🔴 填文案前必读）

| | 小红书 | 微博 | 播客 |
|---|---|---|---|
| 标题 | ≤20 字，**是搜索入口**，要带关键词 | 无独立标题 | 单集标题 ≤60 字 |
| 正文 | ≤1000 字，参与搜索排名，**不是可选项** | **≤140 字**，超了折叠成「展开全文」 | shownotes ≤800 字 |
| 标签 | `#标签`（无尾井号），≥4 个 | `#话题#`（**前后都要**），≥2 个 | 无 |
| 图片 | 6-16 张轮播，主战场 | ≤4 张（自动九宫格） | 单张封面 |
| 链接 | 正文不能放外链（会被限流），引导「主页」 | 可放，自动转 t.cn 短链**占约 25 字** | shownotes 可放 |
| 发布 | CDP 填好，人工点「发布」 | CDP 填好，人工点「发送」 | 自建 RSS，平台侧抓取 |

**易错点**：

- 🔴 **小红书字数不能用 `len()` 算**。平台的算法是「中文 / emoji / 中文标点 = 1 字，英文数字 = 0.5 字，空格不计」，引擎里是 `xhs_char_count()`。两套规则不一致会把合规标题误判超长（晨报 2026-07-08 踩过：用 UTF-16 长度二次裁剪，把已卡好 20 字的标题切断了）。
- 🔴 标签格式两边**反着**：小红书 `#读书`，微博 `#读书#`。写反了 verify 会拦，但别指望它——两套文案分开写，不要复制粘贴改一改。
- 🔴 微博的 140 字算的是**全文**，标签和短链都计入。留出余量。
- 🔴 小红书正文放外链会限流。原文入口靠「主页简介」或评论区，不写进正文。

## 各渠道执行要点

### 小红书

1. 先按 [xhs-storyboard.md](xhs-storyboard.md) 产 `dist/xhs/xhs-outline.md`（金句锁定 → 情绪曲线 → 分镜编排）。
2. 交 `baoyu-xhs-images` 生图，输出到 `dist/xhs/images/`，分辨率 1K（1242×1660）。
3. 正文文案**不是图片的说明文字**，是独立的一段——首句要能单独抓住划到的人。
4. `dispatch --confirm` 调 profile 里 `post_script` 指的 CDP 脚本，开 Chrome 填好标题/正文/图，停在发布页等作者点。

> 小红书没有开放发布 API，但创作服务平台的网页端可以被 CDP 驱动。所以既不是"全自动"，也不是"只能手动复制粘贴"——是**填好等你点**。

### 微博

1. 图直接复用小红书那套的前 4 张，不另生成。
2. 正文写法：**一个完整的判断 + 一个具体数字或细节**。不写"点击阅读全文了解更多"这种话。
3. `dispatch --confirm` 走 `baoyu-post-to-weibo` 的 `weibo-post.ts`。
   > 🔴 别因为"微博 API 要 OAuth、token 5-7 天就过期"退回半自动——那个结论只对官方 API 成立。CDP 走真实浏览器会话，没有 token 过期问题。
   > 该脚本路径在 baoyu 插件缓存里，**目录名带版本 hash，插件一升级就变**，所以引擎是递归查找而不是写死。

### 播客

1. **音频在本机生成，不在 VPS 生成**。VPS 是 headless 机器，NotebookLM 的 cookies 只能是从本机 scp 上去的静态快照，Google 在 1-3 小时内主动判废——晨报踩了一年。文章音频不需要无人值守，本机跑登录态是新鲜的，直接绕开这个坑。
2. **喂裸定稿 markdown 给 NotebookLM，不做二次提炼**——晨报链路验证过，提炼一遍反而丢细节。
3. 🔴 **主持风格提示词必须新写**（profile 的 `podcast.focus_prompt` 指向它）。晨报那份是"双主持播报 10 条要闻"的节奏，文章是"两个人聊透一个话题"，照搬会得到结构很怪的节目。
4. 生成 → 转码 mp3 → **连同同名 `.json` sidecar** 一起 scp 到 VPS 的 `episodes/` → 重建 `feed.xml` → 平台侧 1-12 小时抓取。
   > 🔴 sidecar 不可省。`publish_to_podcast.py` 对没有 sidecar 的文件要求文件名是纯 `YYYY-MM-DD.mp3`，否则**静默跳过**；就算侥幸进了 feed，描述也会套用晨报的"今日 10 条要闻"。
5. 现阶段与晨报**共用一个频道**（订阅量还小，分流不划算），单集标题用 `深聊 | ` 前缀区分。

## 渠道适配器接线状态

| 渠道 | 状态 | 说明 |
|---|---|---|
| 小红书 | ✅ 已接线 | 复用自建的 `xiaohongshu-post.ts`（晨报一直在用） |
| 微博 | ✅ 已接线 | 复用 `baoyu-post-to-weibo` 的 `weibo-post.ts` |
| 播客 | ⬜ 待接线 | feed 已支持混播；还差本机生成链路与 `focus_prompt` |

未接线的渠道 `dispatch --confirm` 明确 exit 3，**不写假装成功的桩**——状态机记下一次没发生过的发布，比不发布更糟。

## 铁律

1. **上游漂移即失效**：`定稿.md` 一变，所有已生成的分发文案标记过期，`verify` 与 `dispatch` 双双阻断。改了文章就得重做文案，没有例外。
2. **没有 receipt 就不算发过**：状态机只认凭证文件，不认口头登记。
3. **`dispatch` 默认 dry-run**：真跑要显式 `--confirm`，且**脚本永远不替作者点最后那下发布**。
4. **私有值只进 profile**：账号名、发布脚本路径、feed 主机属「私有但非密」，与品牌 token 同层；密钥仍然只走 `.env`。公开仓的 `profile.example` 只留占位。
5. **不重复造轮子**：晨报侧已经跑通的东西（发布脚本、文案格式、字数算法）直接复用，不另写一套。两套实现迟早会漂移。
