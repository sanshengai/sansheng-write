# 一稿多投：小红书、微博与播客

> 本模块默认关闭、按篇触发。公众号与网站发布完成后，只有用户明确说「转小红书」
> 「发微博」「一稿多投」时才进入；拿到永久链接本身不等于授权分发。

## 1. 边界与入口

- 上游唯一真源是文章目录里的 `定稿.md`、`article-meta.yaml` 与正式链接。
- 社媒不是把全文缩短，也不是截取公众号配图。每个平台都要重新完成一次「选主张 -- 编故事 --
  写文案 -- 做图片 -- 预填发布页」。
- 小红书与微博的最后一次「发布 / 发送」永远由作者点击；脚本只负责预填与留凭证。
- 只点名一个渠道时只做该渠道，不顺带生成另一个渠道。
- `finalize` 不自动规划小红书或微博；显式触发后运行：

```powershell
python scripts/distribute.py --dir <文章目录> plan --only xhs,weibo
```

## 2. 先确定传播命题

图片也是一篇文章。开始写卡片前，先用一句话写清：

1. 这组图只讲什么？
2. 读者滑完会多知道什么、相信什么或能做什么？
3. 哪个具体事实、机制、对比或结果能证明它，而不是只靠形容词？

一套图只保留一个传播命题。产品 / Skill 推广优先采用下面的九页骨架：

| 页 | 本页唯一任务 | 必须回答 |
|---|---|---|
| P1 | 结果钩子 | 它最终替读者完成了什么？ |
| P2 | 旧方法的痛点 | 为什么现有做法费时、易错或结果不稳？ |
| P3 | 核心机制 | 它靠什么不同的方法解决，不只说「更智能」？ |
| P4--P6 | 三个最强卖点 | 每页一个功能 + 工作方式 + 可验证结果 |
| P7 | 真实流程 / 示例 | 输入什么，经过什么，交付什么？ |
| P8 | 适用人群与获取方式 | 谁最值得用，在哪里可获得？ |
| P9 | 收束与行动 | 给一个低摩擦、符合平台规则的下一步 |

普通观点文章可把 P4--P6 换成三段证据链，把 P7 换成方法或行动清单。张数可随内容在
6--10 张内调整，但不能为了凑数重复同一个观点。

每页交付合同：

- 一个结论式页标题，不能是「亮点一」「更多功能」这类空标题。
- 1--3 个支撑点；每个点尽量包含对象、动作与结果。
- 一个主视觉隐喻或信息结构；装饰不能抢过信息。
- 单页独立可读，连续滑动又有因果或递进关系。
- 删除本页后若整套叙事没有损失，这页就不该存在。

## 3. 两个平台分别设计

| 维度 | 小红书 | 微博 |
|---|---|---|
| 图片比例 | 3:4 竖版，建议 1242×1660 | 1:1 方图，建议 1200×1200 或更高 |
| 图片数量 | 6--10 张常用，脚本允许 6--16 | 4--9 张，优先 9 张完整九宫格 |
| 文案职责 | 补充图片没有展开的背景、体验与讨论问题 | 首段先给完整结论，后文展开机制、亮点、链接和话题 |
| 排版能力 | 纯文本换行、emoji、项目符号；不支持公众号式富文本 | 纯文本换行、编号、emoji、#话题# 与链接；不支持公众号式富文本 |
| 链接 | 不放 URL、二维码或站外搜索指令 | 可在正文中给 GitHub、官网或原文链接 |
| 图片目录 | `dist/xhs/images/` | `dist/weibo/images/` |

🔴 两个平台必须分别生成图片。小红书 3:4 卡片不得截方、加边后冒充微博图；微博方图也
不得直接塞进小红书。文字结构、留白和阅读距离不同，复用会同时损害两端效果。

### 小红书正文

- 标题先给结果、反差或具体收益，不复述公众号标题。
- 正文用 3--6 个短段落：共鸣 / 判断 -- 补充信息 -- 适用人群 -- 站内讨论问题。
- 标签使用 `#标签`，不要写成微博的 `#话题#`。
- 允许中性事实说明，例如「项目已在 GitHub 与品牌官网公开」；不要给网址、二维码，
  也不要写「去搜」「看主页」「私信」「回复关键词」「领取 / 下载」等站外行动指令。
- 若无法确认平台当前规则，采用更保守版本并在发布页人工复核。

### 微博正文

- 140 字是首屏预算，不是全文上限。第一段必须独立说清结论，不能只写悬念。
- 后文用短段落与 ①②③ 编号展开，常见完整长度为 300--1200 字；脚本硬上限默认 5000。
- 先写读者收益，再写 3--6 个具体功能 / 证据，最后放 GitHub、官网或原文链接。
- 标签使用 `#话题#`，通常 2--4 个；不要让标签挤进开头。
- 九张图应完整覆盖传播命题，不以「前四张够发」为目标。

## 4. 视觉生产合同

视觉方向由本 Skill 决定，像素生成只交给 `baoyu-image-gen`。风格与布局按页内容灵活选择，
不把所有页面锁成同一模板；同一套必须共享色板、字体气质、线条语言与品牌位置。

通用要求：

1. 先做一张 P1 试片，验收信息层级、中文正确率、色彩与品牌位置。
2. 试片通过后，若总图数 ≥4 且当前 provider 支持批处理，使用 batch 模式提交全部 canonical
   prompts；provider 不支持时才按同一提示词串行渲染。
3. 每张图的可见中文、插画 / 图表与可选品牌 logo 必须在同一次原生生图请求中完成。
4. 禁止先生成无字底图，再用 SVG、HTML、Canvas、Pillow 或另一模型补字；也禁止把两种生成器
   拼在一张图里。
5. logo 作为参考图随请求提交，固定在同一安全区（默认左上角），尺寸与留白跨页一致。
6. 错字、漏字或版式失败时，修正 canonical prompt 后整张重渲；不做后期补丁。
7. 全套完成后逐张检查：文字、观点、页序、比例、重复内容、logo、一致性与缩略图可读性。

推荐视觉基线是低饱和、克制的编辑设计：米白 / 灰蓝 / 棕红等有限色板，正文高对比，强调色
只服务关键数字或结论。retro、notion、minimal 等只是视觉语言，不决定页面信息密度；页面布局
应在 sparse、comparison、flow、list、dense 等结构之间按内容切换。

## 5. 文案文件格式

`dist/社媒文案.txt` 与晨报使用同一种分段格式：

```text
════════════ 小红书 ════════════

# 标题

<不超过 profile 设定上限>

# 正文

<正文；末尾放 #标签>


════════════ 微博 ════════════

# 正文

<首段不超过 140 字且独立成立>

<后续完整展开>

GitHub：<链接>
官网：<链接>

#话题一# #话题二#
```

编辑器不渲染 Markdown 标题、加粗、表格或卡片。上面的 `# 标题 / # 正文` 只是本地解析标记，
发布脚本会把实际内容填进平台的纯文本框。

## 6. 校验与预填

```powershell
# 先生成指定渠道计划
python scripts/distribute.py --dir <文章目录> plan --only xhs,weibo

# 文案和图片完成后分别校验
python scripts/distribute.py --dir <文章目录> verify xhs
python scripts/distribute.py --dir <文章目录> verify weibo

# dry-run 只展示将执行什么
python scripts/distribute.py --dir <文章目录> dispatch xhs
python scripts/distribute.py --dir <文章目录> dispatch weibo

# 预填浏览器；仍不点击最终发布按钮
python scripts/distribute.py --dir <文章目录> dispatch xhs --confirm
python scripts/distribute.py --dir <文章目录> dispatch weibo --confirm
```

`verify` 会检查渠道专属目录、张数、3:4 / 1:1 比例、文案长度、标签格式与小红书导流风险。
定稿发生变化后，旧文案与旧图片自动视为过期，必须重新 plan、verify。

## 7. 播客

播客仍以 `定稿.md` 为内容上游。只有 profile 明确设置
`podcast.auto_after_finalize: true` 时，`finalize` 才会把它当成长期授权自动生成并推送
RSS；否则同样按篇显式运行。音频生成、shownotes、feed 与 receipt 规则见
`scripts/podcast_episode.py` 的命令帮助。
