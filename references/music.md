# 文章音乐（BGM / 主题曲）

## 当前执行方式：MiniMax 网页手动生成

默认由作者在 MiniMax 网页生成中文人声主题曲。Lyria 自动通道目前暂停，直到作者明确要求恢复；不运行自动生成器，不为推进文章要求作者登录 Google Cloud、配置 ADC、项目或 API Key，也不改走 MiniMax API。暂停的是自动生成通道，主题曲本身仍是发布必需素材。

Agent 必须先完成可直接使用的 `MiniMax-主题曲生成单.md`，再请求作者操作。不能只说“去生成一首歌”，也不能只给主题而缺完整歌词。模板见 `../templates/minimax-music-brief.template.md`。

### 1. 交付生成单

从已确认正文提炼，先明确文章对象、读者最应记住的问题和可入歌的具体场景，再确定歌名、歌词、风格与两张封面的构想，不先套一首通用抒情歌。文件保存在本篇文章目录，并给可点击的绝对路径。必含：

- 歌名：让读者直接辨认文章的对象或核心问题，适合唱出，不照搬整条文章标题；具体取法见下方「主题与歌词写法」。
- 主题与情绪：用具体生活画面说明要唱什么、情绪怎样变化，避免把技术说明直接塞进歌词。
- 与本文的对应：歌名和副歌对应哪些具体内容，风格为何适合这篇；不能只有「省时间、温暖、治愈」等泛用理由。
- 可直接复制的音乐风格提示词：人声、语言、BPM、配器、氛围、段落结构、目标时长及应避免的唱法。
- 完整简体中文歌词：按主歌、副歌、桥段、尾声等实际结构写全，风格和歌词分开，便于分别复制。
- 导出与回传要求：MP3 文件名、放置目录；保留网页实际显示的模型名称或生成记录，便于登记来源。不要把建议时长或计划模型当成成品事实。

**复制格式固定**：歌名、音乐风格提示词、完整歌词各放在一个独立的 `text` 围栏代码块中，方便分别一键复制。歌名块只含歌名本身，不加中文或英文引号、书名号，也不带「歌名：」前缀。风格块只含可粘贴的提示词；歌词块只含完整歌词及必要的演唱段落标记。小节标题、创作说明、对应关系和操作提示都放在代码块外，不能混入待复制内容，也不能只用普通段落或加粗代替复制块。

作者已有歌名、风格或歌词选择时沿用。新歌按下方品牌音乐 DNA 与风格池编写；已审批正文及 meta 不因制作生成单而改写。

**时长：新主题曲目标为 2 分 30 秒至 3 分 30 秒（150–210 秒），默认按约 3 分钟规划。** 风格提示词与生成单都写明范围；按语速、留白和副歌重复量安排歌词，不机械套满所有段落。段落长短、是否加桥段由内容决定，避免长前奏或反复加唱撑时长。收到 MP3 后用实际音频探测确认；超出范围时调整生成或剪辑方案，不能把目标时长登记成实测，也不能直接截断唱到一半的句子。此范围用于新主题曲，不限制长文播客，也不追改历史歌曲的实际记录。

### 2. 等待 MP3 时

给出完整生成单后，等待作者提供实际音频，继续可独立完成的配图、核对等工作。此时 BGM 仍待完成，不标失败、不 `skip`、不造 MP3 或来源凭证、不承诺草稿已提交。收到音频后直接续做，不重新要求正文审批。

### 3. 接收音频与来源登记

核实可播放文件与实际时长、来源后，使用 `music_manifest.py` 创建 `_music-manifest.json`，绑定文件 SHA-256、字节数、时长以及真实 `provider/model/mode`。文件名、时间戳、生成单里的计划字段和“最新候选”均不能证明实际来源。

若没有既有歌曲注册表，可先在本篇建立 `主题曲来源记录.md`，以独立条目记下作者交付事实、实际模型和文件；manifest 引用该文件和条目。已有注册表时复用，不复制另一份。模型版本只是来源备注，不作为制作前置条件：优先采用作者已提供的信息或文件内可核实的元数据；版本缺失时将 `origin.model` 如实登记为 `未提供`，在来源记录说明已知与未知，继续制作，不仅为补版本追问或暂停。作者主动补充后再更新记录，不把计划模型、历史歌曲版本或平台默认版本当作本首事实。

```bash
python "$SKILL/scripts/music_manifest.py" create "<文章目录>" --audio "<实际 MP3 相对路径>" --title "<歌名>" --duration-seconds <探测时长> --provider "MiniMax" --model "<网页实际模型>" --mode "web-ui" --registry-ref "主题曲来源记录.md" --registry-entry "<实际条目 ID>"
python "$SKILL/scripts/music_manifest.py" verify "<文章目录>" --probe-duration
```

发布硬门保持通道中性：作者明确指定复用既有歌曲或其他来源时保留真实出身，不把旧歌改写成 MiniMax 新生成。

## 品牌音乐 DNA

本号的音乐基调：**温暖 · 有机 · 克制 · 舒缓空灵 · 中文人声（Mandarin vocals）**

### 全局情绪约束

| 维度 | 约束 |
|------|------|
| 默认能量级别 | calm（10 分制 3-4 分），**绝不欢快、无强节奏感** |
| BPM | 全部锁 55-68（舒缓区），不超过 70 |
| 风格倾向 | 环境浮声 / 氛围钢琴 / 空灵 / 温暖怀旧；默认 `beatless`，`shanghai_jazz_soul` 只允许非推进型轻刷鼓 |

> 🔴 **必须含中文演唱**--人声唱出文章内容，让读者直觉感到"这首歌是专为这篇文章创作的"，与文字内容一一呼应、有专属感与震撼感。纯器乐辨识度太低、给不了这种呼应，**不采用纯器乐**。

### prompt 关键词（研究固化）

- **默认必带**：`ambient / ethereal / serene / gentle / spacious / lush reverb / soft dynamics / minimalist`、具体软音色（felt piano / ambient pad / glockenspiel）、明确 BPM
- **海派爵士灵魂例外**：改用 `classic Shanghai jazz / gentle soul / vintage room / restrained phrasing / feather-light brushed drums`，结构写明「怀旧主歌 → 柔和发亮副歌」
- **禁用**：`energetic / upbeat / fast tempo / driving beat / heavy bass / EDM / rock / aggressive / festive / cheerful pop`

## 风格池（5 种舒缓系，与 generate_article_bgm.py 的 STYLE_POOL 同步）

| 风格 Key | 名称 | BPM | 适合文章类型 |
|----------|------|-----|------------|
| `ethereal_folk` | 空灵民谣 | 60 | 深度思考 / 观点输出 / 人物说理 |
| `ambient_vocal` | 环境浮声 | 55 | 科技探索 / 未来想象 / AI工具对比 / 前沿趋势 |
| `ambient_piano` | 氛围钢琴 | 58 | 哲思文章 / 行业反思 / 年度盘点 / 收尾感悟 |
| `cinematic_vocal` | 影视人声 | 64 | 长文特稿 / 行业深度分析 / 重磅专题 / 年终总结 |
| `shanghai_jazz_soul` | 海派爵士灵魂 | 68 | 人物往事 / 城市记忆 / 怀旧叙事 / 温柔纪实 |

> 仍停用原 `light_pop`（欢快）/ `lofi_vocal`（通用节拍）/ `warm_ballad`（叙事节奏）。
> `shanghai_jazz_soul` 不是恢复通用 lo-fi 节拍：它只在 68 BPM 下允许轻刷鼓作呼吸脉冲，明确禁止 driving beat、鼓 fill 和大乐队式炒作。
> 风格选择：先按本文的叙事、情绪与歌词节奏选择风格，再读 `<数据目录>/articles.md` 近 3 篇「音乐风格」字段比较。优先用同样适合本文的不同风格、配器或演唱处理拉开区别；不能只因轮到某种风格就套用。若同一风格最合适，生成单写明理由，并在配器、乐句或结构上作出实质区别。人声交替与舒缓基调继续保留。

### 人声交替（防审美疲劳）

| 维度 | 规范 |
|------|------|
| 交替规则 | 默认奇数篇=女声，偶数篇=男声（按目录序号）；`shanghai_jazz_soul` 无显式设置时默认亲密女声 |
| 女声 | 空灵、气声、偏高音区（温柔一面） |
| 男声 | 温暖、中低音、叙述感 |

## 主题与歌词写法

先提炼文章的对象、核心问题与具体场景，再取歌名、写歌词。歌名优先取文章的辨识点：产品或人物名、关键动作、核心矛盾；可以与一个可唱的意象组合，不固定套同一种公式。只有「时间、远方、灯光」这类通用情绪时，读者很难知道对应哪篇文章，应改成能指向本文的名字。若隐喻需要读完生成单里的解释才能理解，就应在歌名中补上明确的主题线索。

主旨落到具体动作和物件，再写可唱的句子。主歌展开本文的场景，副歌保留与核心问题有关的动作或句子；不能只在标题加一个产品名，歌词仍可套给任何文章。歌词要有人的处境、动作和情绪变化，避免把说明书逐条改成韵文，也不为押韵扭曲意思。朗读检查句子是否自然、长句是否能换气，副歌是否既好记又贴题。保留文章的能力边界，不为好唱而把概率判断写成必然正确，或把程序负责的动作写成模型自行完成。软件名可以自然出现，不强制每首唱出，也不把「不必唱命令和参数」扩大为回避文章对象。由当前 Agent 写完整歌词，不把此步骤交给尚未启动的 Lyria。

交付前做一次换题检查：把歌名和副歌移到另一篇无关文章，如果基本不需修改，说明关联仍太弱，应一起重写。生成单用一两句说明歌名、副歌分别对应本文什么内容；这段说明用于自检，不能替代歌名和歌词本身的辨识度。

## 主题曲与播客封面：画锚点，按图标出图（2026-09-23 修订）

### 为什么改：108 篇的价签和路标

2026-09-22 的「图标逻辑」解决了一排缩略图分不开的问题：深底、单主体、无字。但 108 篇
（Opus 5.5 与 GPT-6 Sol）出来的是一张剪开的价签、一块指向两边的路标，作者的判断是
「没有任何标识度，看不懂」。原因不在画工，在**取材**：两张图画的都是标题冒号后面那句**论点**
（「砍半价」「方向相反」）。论点是抽象关系，画成物件只能是通用隐喻——价签、路标、天平、台阶、
钥匙、灯泡——而通用隐喻换到任何一篇讲降价、取舍、进阶的文章都成立，等于没有指认。

封面出现的地方（官网播放器 46 px、歌单 62 px、播客列表 66 px、微信音频卡）**旁边永远有一行标题**。
所以封面不必独自讲清文章，它的任务是和旁边那行字**押上韵**：读者扫到标题里的专名，
再看图，立刻对上。标题公式已经保证每篇都有这个专名（`关键词锚点`）。

**一句话规则：封面画锚点，不画论点。** 锚点是标题竖杠后、冒号前那个专名（人、公司、产品、书、事件）；
论点是冒号后那句话。

### 怎么把一个专名画出来（四条路线，按优先级）

`_audio-cover-plan.json` 每张封面必填 `identity.route`，只能是下面四种：

1. **实物外形**：锚点本身有公认外形——一台车、一台电视、一本书的开本和颜色、一座建筑、一件标志性物件。
   真人不生成肖像（铁律），改画他公认的标志物件。
2. **名字字面义**：名字自带意象、且**中文读者一眼能懂**时才用——中文名本身（「曾国藩」的「曾」字、
   瑞幸的鹿、京东的狗）或人人认识的英文词。🔴 108 篇实测：单画一轮太阳想代表 Sol，46 px 盲配被认成
   Grok 那篇的「发布爆点」——读者不知道 Sol 是太阳。外文字面义一律再叠一个标号（太阳上写 Sol）。
3. **官方视觉**：借厂商公开视觉的**颜色与基本形**呼应（某家的橙色星芒、某产品的主色），
   但不复刻 logo 的具体造型——封面是评论配图，不能冒充品牌。
4. **标号**：版本号或单字本身就是识别物（4.7、5.5、「曾」）。允许在 `glyph` 里写**一个**短标号，
   非空白字符 ≤ 4、必须在标题（主题曲可用歌名）里原样出现，由生图模型把它做成主体的一部分、
   同材质同光；46 px 下 2–3 个大字符认得出，整句标题认不出，所以只放标号不放标题。

两张封面分工：**播客封面画文章锚点**（这期聊的是谁 / 什么），`identity.anchor` 必须在文章标题里；
**主题曲封面画歌名里的锚点加这首歌的时刻**（同一个专名在什么情境里），`anchor` 可取歌名或标题。
歌名按上文要求本来就要能指认文章，封面跟着歌名走。两张主体仍然必须不同。

对比类文章（A 对 B、A 与 B）锚点本身是两样东西，允许**一对并置主体**当作一个主体，
例如两块分开的底座分别托着 5.5 和 6。并置时要写明「中间留出明显空隙」，否则模型会把两个标号挤成一个数（108 篇第一版出成了「5.56」）。

### 禁止与放行

- 路线优先级的实际含义：**标号最稳**（46 px 下 2–3 个大字符认得出，且只可能属于这一篇），
  实物外形其次，字面义与官方视觉只在读者确实认得时才单独成立。拿不准就叠标号。
- 论点隐喻道具（天平、路标、岔路、价签、台阶、梯子、钥匙、锁、灯泡、齿轮、拼图、沙漏、指南针、
  桥、箭头、靶、放大镜、砝码……）脚本直接拦；**只有标题或歌名里字面出现这个词**时才放行。
- 窗、台灯、书本、河、船、落日、耳机、麦克风、星空、月亮这类通用景物，只有歌词、正文依据或
  `identity.reason` 里真有它才允许（例：Luna 的字面义就是月亮）。
- 形式要求不变：深底 + 一个强调色（`ink / ember / moss / plum / ocean / rust / slate / sand`，
  两张不同，主题曲避开前三篇）、主体居中占约 2/3、不裁切、无场景无第二件道具、大块面高对比；
  渲染质感 `sculpted`（默认）/ `papercut` / `flat` / `painted`。

### 规划文件（schema 3）

```json
{
  "schema_version": 3,
  "theme_cover": {
    "subject": "夜色中央一轮金色太阳，太阳正面浮雕着 Sol 三个字母",
    "lyric_anchor": "隔了一百零一分钟",
    "article_anchor": "正文中的具体原文",
    "identity": {"anchor": "Sol", "route": "标号", "reason": "歌名是 Opus 和 Sol 同一夜，太阳上直接写着 Sol"},
    "glyph": "Sol",
    "palette": "ink",
    "render": "sculpted"
  },
  "podcast_cover": {
    "subject": "左右两块分开的立体底座分别托着数字 5.5 和更高的数字 6，两块之间留出明显空隙",
    "article_anchor": "正文中的具体原文",
    "identity": {"anchor": "5.5", "route": "标号", "reason": "标题里就是 Opus 5.5 与 GPT-6"},
    "glyph": "5.5 6",
    "palette": "rust",
    "render": "sculpted"
  }
}
```

`article_anchor` 至少 8 字符、必须是 `定稿.md` 原文；`lyric_anchor` 必须是生成单里真实的歌名或歌词句；
`identity.reason` 至少 8 字，写清「读者凭什么一眼想到锚点」。`audio_covers.py` 核对全部规则，违规直接报错。

### 验收：盲配测试（看 46 px，不看原图）

出图后脚本写 `_audio-cover-thumbs.png`（256 / 128 / 64 / 46 px）。形式验收照旧：46 px 下轮廓还在、
两张一眼分开、和前三篇并排不像同一套、没有多余文字或第二件道具。

**新增盲配**：派一个没有本文上下文的看图子 Agent，只给 46 px 的两张缩略图和一份打乱顺序的
6 个标题（本篇 + 作品库最近 5 篇），问「这两张各属于哪篇」。**两张都配对才算过**；配错就说明
图没画出锚点，改 `subject` / `identity` 后 `--force` 重出。这一步是图版的「换题检查」——
歌词要求换到别篇不成立，封面同理。结论（子 Agent 的原答、配对结果、改了什么）写进
`_audio-cover-review.md`。修改已有封面走 `--force` 或 handoff 的 `--regenerate-covers`；
不自动改动历史已发布图片。

## 接入微信文章

音频文件与 manifest 验证通过后，用 `audio_cards.py::upsert_card` 的共享模板写入主题曲卡片。必须在 MD→HTML 排版之前完成；AUDIO-CARD 与可选 PODCAST-CARD 机器块先收口到 `定稿.md` 最末尾，再由 `format_layout.py --all` 按「导读 → 主题曲 → 播客 → 正文」前置。不得改动已审批的作者正文。主题曲封面按既有视觉流程处理；封面不能证明音频已经生成。

若 `podcast.wechat_embed: true`，`podcast-pregen` 会用同一模板再写「🎧 音频版本｜本期播客」卡片。发布时在微信编辑器分别插入两份原生音频；保存后直接跑 `pipeline.py wechat-audio-check`。

### 上传文件统一放在文章文件夹

运行以下命令，把人工上传用的主题曲、播客和封面放在本篇文章目录第一层（例如 `100-AI帮自己搬家/`），交付时给按项目规则同步后的主仓文章目录及其中音频的可点击路径（worktree 仅作制作目录），不另建“手工上传”文件夹：

```bash
python "$SKILL/scripts/pipeline.py" --dir "<文章目录>" handoff-assets
```

作者上传时只看文章编号文件夹第一层，不要再进 `素材/` 找音频封面：

| 上传什么 | 文件名 |
|---|---|
| 公众号头图 | `cover.png`（生成源仍是 `素材/cover.png`，第一层是同一份副本） |
| 主题曲 | 歌名原文件名，例如 `对标那一档.mp3` |
| 主题曲封面 | `音乐封面.png` |
| 播客 | `播客 \| {文章标题}.mp3`，标题用定稿标题，竖线保留 |
| 播客封面 | `播客封面.png` |

`handoff-assets` 先跑 `audio_covers.py` 缺哪张生成哪张（走 `renderer-policy.json` 同一条 baoyu-image-gen 链，不加水印，`--regenerate-covers` 才重生成），缺封面直接拒绝交付。新封面直接写在第一层，不写进 `素材/`。旧稿若只有 `素材/bgm_cover.png` 或 `素材/podcast_cover.png`，交付时复制成上表的文件名，不删旧文件。`dist/podcast/audio.mp3` 仍是官网和 RSS 取字节的机器副本；推到 feed 主机的文件名与第一层播客文件名相同。`素材/` 只放正文插图。

命令只读取封存视觉凭证和音频 manifest 指定的文件，验证后才交付，根目录写 `_handoff-receipt.json`；同一快照可重复运行，现有同名不同内容文件会报错，不静默覆盖正文或其他资产。旧 `SANSHENG_WRITE_HANDOFF_DIR` 配置不再自动生效。只有作者明确要求独立导出时才使用 `--target-root <目录>`，此模式保留 `--revision r2` 的版本快照能力。

这里的交付不等于永久归档；整篇成品归档仍按 `physical-archive.md` 执行。
